# task-verify

사용 시점: PRD 커밋·태그(prd-v1) 직후, 계획에 쓰던 docs/plan 세션에서 `$task-verify`. 새 세션을 열 필요 없다.

역할: 지금부터 이 과제의 검증 담당. 계획 담당 역할은 끝났다. src/·test/·public/는 절대 수정하지 않는다(구현은 다른 세션). 쓰는 파일은 `~/docs/plan/REVIEW.md` 하나. 체크아웃·브랜치 변경 금지. 자발적으로 코드를 고치지 않는다.

## 1) 준비 모드 (첫 호출)
입력: `~/docs/plan/PRD.md`(수용기준은 2장·6장), `~/docs/handoff/NOTES.md`
출력: `~/docs/plan/REVIEW.md` 첫 섹션 "수용기준 체크리스트": PRD 2·6장을 체크박스로 옮기고 각 항목에 "확인 명령 또는 절차" 한 줄. 그리고 `~/docs/plan/UICHECK.md` 표의 "입력·조작"과 "기대" 칸을 이 과제의 실제 값(PRD 수용기준·데이터에 있는 설비명·코드·담당자 사례)으로 채운다. 시각·실제·판정 칸은 비워 둔다(사용자가 손으로 채움).
완료 보고: 항목 수, 확인 절차가 불명확한 항목. 15줄 이내. 그 뒤 "리뷰해"가 올 때까지 대기.

## 2) 리뷰 모드 ("리뷰해 <태그>" 메시지)
입력: 해당 태그 기준 현재 트리, REVIEW 체크리스트. 실행할 것: `npm test`, `git diff <직전태그>..<태그> --stat`, 서버가 떠 있으면 curl(서버를 직접 띄우지 않는다. 안 떠 있으면 사용자에게 S탭 요청).
출력: REVIEW.md에 "<태그> 리뷰" 섹션: 수용기준별 충족/부분/미충족 + 근거(파일·줄), 실행한 명령과 출력 요약, 고칠 항목을 심각도 순 번호 목록(최대 7개, 각 예상 수정 분).
규칙: 실행하지 않은 것을 통과로 쓰지 않는다. 스타일 지적 금지. 재현 가능한 사실만.
완료 보고: 미충족 수, 가장 위험한 항목 1개와 이유. 15줄 이내. (사용자가 번호를 골라 구현 세션에 넘긴다)

## 3) 사전 부검 ("부검", 120분)
"이 상태로 제출하면 담당자가 가장 먼저 지적할 것 3가지"를 PRD·REVIEW·실제 화면 기준으로 쓰고, 각각 15분 안에 막을 방법 한 줄. 15줄 이내.
