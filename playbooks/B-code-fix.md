# 플레이북 B — 기존 코드 수정 (버그·기능 추가)

신호: src/·test/가 이미 있고, 실패하는 테스트나 버그 보고, 기능 추가 요구가 있다.

> 이 각본은 **출발점이지 명령이 아니다.** 온보딩에서 항목마다 "그대로 / 바꿈 / 버림"을 사용자와 정한 뒤 쓴다. 과제가 각본과 다르면 과제를 따르고, 차이를 RUNPLAN에 적는다.

## 순서 (고정)

1. **읽기만**: 실행·테스트 명령 확인 → `npm test`(또는 해당 러너) 실제 실행 → 실패 목록과 각 실패의 원인 가설을 NOTES에 먼저 기록. 코드는 아직 안 고친다.
2. 테스트를 고치지 말고 코드를 고친다. 실패 1개 = 커밋 1개. 커밋 메시지에 "원인 → 수정".
3. 기능 추가는 기존 패턴을 따른다(같은 파일 구조·같은 테스트 방식). 새 테스트부터 쓰고 구현.
4. 환경 요구(0.0.0.0 바인딩, PORT, 인코딩 BOM 등)는 README에 숨어 있는 경우가 많다. 체크리스트로 먼저 뽑는다.

## v0 정의 (45분)

실패 테스트 전부 통과 + 환경 요구 충족 + 커밋. 기능 추가는 v0 이후.

## 기능 루프 후보

1. README가 명시한 추가 기능(테스트 포함)
2. 담당자가 말한 운영 요구(헬스체크, 로그, 기본 목록 규칙)
3. 기존 테스트와 충돌하는 요구 → 담당자와 조율해 결정, NOTES에 기록

## 검증 포인트

- `git diff --stat`로 테스트 파일이 바뀌지 않았는지(테스트 수정 금지)
- 고친 뒤 전체 테스트 재실행(회귀)
- 입력 검증에서 막는 경우/안 막는 경우 구분과 위험 기록

## 흔한 함정

- 테스트를 "통과하게" 고치는 것 → 금지
- 리팩터링 유혹 → v0 전에는 금지
- 완료 보고만 믿기 → `npm test` 실제 출력과 diff로 확인
